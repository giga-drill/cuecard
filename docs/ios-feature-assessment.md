## 结论

横竖屏布局可以在 CueCard 上直接扩展，复杂度低到中等。

语音跟读不是简单地把语音转成文字。一个可用版本至少包含实时语音识别、文稿位置匹配、停顿处理、滚动平滑、识别任务恢复和音频中断处理，复杂度中高。真正需要先验证的系统边界是：CueCard 进入画中画后在后台使用麦克风，同时前台的系统相机、抖音或其他录制 App 也使用麦克风时，两个 App 能否稳定共存。iOS 会仲裁相互竞争的音频会话，不能在没有真机验证的情况下承诺对所有第三方录制 App 都兼容。

因此，推荐先做横竖屏，再做一个 1–2 天的真机语音技术验证。验证通过后才进入完整语音跟读实现。

## 当前 CueCard iOS 基线

- 原生 SwiftUI/UIKit 工程，目标为 iPhone 和 iPad。
- 悬浮窗使用 `AVPictureInPictureVideoCallViewController`。
- 主界面按 `wordsPerMinute` 计算当前词位置；悬浮窗按经过时间占总朗读时长的比例连续滚动。
- 已允许主 App 的竖屏和横屏方向。
- 悬浮窗只提供 `16:9`、`4:3`、`1:1`，全部是横向或方形，没有 `9:16`、`3:4`。
- 悬浮窗尺寸只在初始化时计算，没有监听方向变化并重建或更新悬浮内容。
- `scrollSpeed` 虽然保存在设置里，但当前滚动实际主要由 `wordsPerMinute` 驱动。
- iOS 业务源码共有 12 个 Swift 文件、3,616 行；其中提词器页面和 PiP 管理器合计 1,494 行。
- 没有单元测试或 UI 测试目标。

## 基线运行风险

1. 上游工程依赖 Firebase、Google Sign-In、Analytics 和 Crashlytics，但仓库没有提交 `GoogleService-Info.plist`。本 fork 已选择本地优先、无账号路线，并移除这些依赖。
2. 上游工程目标配置同时出现 17.0 和 16.6；本 fork 已按 iOS README 统一为 iOS 17.0+。
3. 上游通过 `UIApplication.shared.perform(#selector(NSXPCConnection.suspend))` 主动把 App 送入后台。这不是应当依赖的公开产品接口；本 fork 已移除该调用，改为启动 PiP 后由用户正常切换 App。
4. 当前没有测试。语音匹配和方向切换都属于容易回归的状态逻辑，新增功能必须同时补测试。

## 为什么不需要 Firebase

Firebase 与悬浮提词、自动滚动、横竖屏和语音跟读没有技术依赖。上游只把它用于：

- Firebase Auth：Apple/Google 账号登录；
- Analytics：页面和按钮事件；
- Crashlytics：线上崩溃收集。

现有文稿和设置本来就保存在本机，并没有依赖 Firebase 同步。对当前个人、本地优先版本，保留 Firebase 只会增加账号配置、隐私披露、网络依赖和构建体积，因此本 fork 已移除登录页、账号管理、Google Sign-In、Analytics、Crashlytics 和对应 Swift Package。代价是暂时没有登录、跨设备同步和云端崩溃统计；这些都可以等产品确实需要时再单独引入，不必绑定 Firebase。

## 功能一：横竖屏悬浮布局

### 建议实现

1. 把悬浮方向建模为 `portrait` / `landscape`，默认 `portrait`。
2. 补充 `9:16` 和 `3:4` 的竖向比例，横屏时使用对应的 `16:9` 或 `4:3`。
3. 监听有效的设备/界面方向变化，忽略 `faceUp`、`faceDown` 和未知方向。
4. 方向变化时更新 `preferredContentSize`；如果系统不接受活动中的尺寸翻转，则停止并重建 PiP，同时保存、恢复阅读进度和播放状态。
5. 主界面控件在窄横屏下改为紧凑排列，避免五个控制按钮挤出屏幕。
6. 用真机覆盖“进入 PiP 前旋转”和“PiP 活动中旋转”两条路径。

### 复杂度与规模

| 项目 | 估算 |
|---|---:|
| 产品代码 | 120–250 行 |
| 测试代码 | 100–180 行 |
| 开发与自测 | 1–2 人日 |
| 真机方向/PiP 验证 | 0.5–1 人日 |
| 综合复杂度 | 低到中等 |

主要不确定性不是 SwiftUI 布局，而是系统 PiP 在活动中改变宽高比时的具体行为。

## 功能二：语音跟读滚动

### “AI 跟读”实际上包含什么

MVP 不需要接大语言模型。核心是 Apple Speech 的流式识别加一个本地文稿对齐器：

1. 从麦克风持续取得音频并获得部分识别结果。
2. 对识别文本和原稿做同样的标准化。中文应按字或适合中文的词元处理，同时兼容数字、英文名和标点差异。
3. 只在当前阅读位置附近寻找匹配，使用编辑距离、连续命中奖励和向前偏好，避免常见词造成远距离跳转。
4. 把“识别到的文稿位置”变成滚动目标，用缓动而不是直接跳动。
5. 停顿约一秒后停止滚动；恢复说话后继续匹配。
6. 处理重复一句、退回重说、跳过一段、临时发挥、识别任务结束、网络/本地模型不可用和音频中断。
7. 请求麦克风和语音识别权限，并显示明确的录音状态。

Apple 的 `requiresOnDeviceRecognition` 只有在当前语言和设备的 `supportsOnDeviceRecognition` 为真时才能保证本地识别；否则必须明确报不可用或允许联网，不能静默改变隐私行为。

### 两条产品路线

#### A. 继续悬浮在其他录制 App 上方

这是最符合当前产品定义的路线，但也是风险最高的路线。提词器在后台需要录音，前台录制 App 也会激活自己的录音会话。Apple 的音频会话机制会对竞争的非混音会话进行中断，因此兼容性可能按 App 不同而变化。

必须先用真实 iPhone 做兼容矩阵，至少验证：

- 系统相机；
- 用户实际使用的短视频/直播 App；
- 有线、蓝牙和手机内置麦克风；
- 横屏、竖屏、锁屏/来电等中断恢复。

如果目标 App 中有任意一个会抢占麦克风，语音跟读会停，而普通定速滚动仍可继续。

#### B. 在本 App 内置相机录制

这是最稳定的语音跟读路线：相机录制和识别共享同一个音频采集流，不与另一个 App 争夺麦克风。代价是产品不再只是“浮在任意 App 上方”，还要实现相机预览、录制、方向、保存、权限和失败恢复。

另一个 MIT 开源项目 Open Prompter 采用这类架构。其成熟语音跟读相关生产代码约 3,431 行，相关测试约 1,175 行，可作为复杂度参照，而不是直接把语音识别当成几十行 API 接入。

### 复杂度与规模

| 交付层级 | 产品代码 | 测试代码 | 时间 | 能力边界 |
|---|---:|---:|---:|---|
| 技术验证 | 350–650 行 | 100–250 行 | 2–4 人日 | 单一语言、短文稿、验证识别和 PiP/麦克风共存 |
| 可用 MVP | 1,000–1,800 行 | 500–900 行 | 7–12 人日 | 中文为主、局部模糊匹配、停顿、重复/小范围跳句、平滑滚动、中断恢复 |
| 稳健产品版 | 1,800–3,000 行 | 800–1,500 行 | 3–6 周 | 多语言、更强跳段恢复、完整兼容矩阵、诊断与性能优化 |

如果选择内置相机路线，相机录制部分还需额外约 1,500–3,000 行产品代码和 2–4 周，具体取决于是否包含前后摄像头、画质、帧率、稳定、防中断和相册保存。

## 两项需求合计

在“外部录制 App + PiP 语音验证通过”的前提下：

- 可用 MVP 新增约 1,200–2,100 行产品代码；
- 新增约 600–1,100 行测试代码；
- 约 9–15 人日，包括横竖屏、语音匹配、状态恢复和目标 App 真机验证；
- 相比现有 3,616 行 iOS 业务代码，产品代码会增加约三分之一到五分之三。

这还不包含移除/替换 Firebase 登录、产品改名、视觉重做、上架资料和长期兼容维护。

## 推荐实施顺序

1. **基线清理（0.5–2 天）**：已确定本地无账号、移除 Firebase并统一为 iOS 17.0+；下一步确保真机能稳定进入 PiP。
2. **横竖屏切片（1.5–3 天）**：实现方向模型、竖向比例和进度无损切换，并在真机验收。
3. **语音共存验证（1–2 天）**：只接最小 Speech 流，不做复杂匹配；验证系统相机和目标短视频 App 是否会抢占麦克风。
4. **产品决策门**：若外部 App 兼容性可接受，继续路线 A；若不可接受，在“仅支持兼容 App”与“内置相机”之间做明确选择。
5. **语音跟读 MVP（7–12 天）**：完成中文文本标准化、局部对齐、滚动协调、中断恢复和单元测试。
6. **真机回归（2–4 天）**：不同机型、方向、麦克风、长文稿、停顿/口误/跳句及目标录制 App。

## 开发前仍需确认

1. **优先兼容的录制 App**：系统相机、抖音、小红书、微信视频号、B 站或其他直播 App，需给出优先级，真机验证不能笼统覆盖“所有 App”。
2. **语音路线的失败策略**：如果目标录制 App 抢占麦克风，是接受“这些 App 退回定速滚动”，还是转为 App 内置相机。
3. **首发语言**：建议先只做普通话中文，英文混读可兼容；多语言会扩大识别和文本标准化测试面。
4. **隐私边界**：建议优先端侧识别；设备或语言不支持端侧时，是明确报不可用，还是允许联网识别。
5. **跟读行为**：停顿多久算暂停、重复上一句是否允许回退、主动跳段如何恢复，需要形成可验收规则。
6. **最低系统版本**：当前已按上游文档统一为 iOS 17.0+；如果希望覆盖更老设备，需要明确提出并重新做 API 兼容检查。
